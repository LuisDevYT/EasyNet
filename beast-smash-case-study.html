Context

The goal was multiplayer that still felt simple to build.

Beast Smash is easy to understand: choose a character, enter a short match, hit opponents and try to be the last one standing. The multiplayer needed to preserve that simplicity for players and for the game code itself.

The team did not want every ability to become RPCs, server checks, client guesses and correction logic. Pressing attack should remain a game action, not a networking feature. At the same time, fairness lives in small moments: a hit, a launch, a recovery, an item, or the second a player loses connection.

The challenge was keeping the code simple, the fight fair and the multiplayer bill small.

Host-client was cheap but fragile. Full server authority was fair but expensive. Beast Smash needed the middle: no player-owned host, no host migration freeze, no full server simulation, and a cost low enough for an ad-supported mobile game.

Decision

EasyNet made the match authoritative without making the server carry the whole game.

EasyNet used a deterministic match model: the server coordinates the room and the ordered match timeline, while every player reaches the same result through the same simulation.

That changed what had to be trusted. A player performs an action, but does not report the result of a punch, launch or KO. The shared simulation decides what happened, so the outcome is not negotiated between devices and is not owned by one host.

Combat can stay normal game behavior: movement, attacks, cooldowns, items, launch force, recoveries and eliminations. EasyNet keeps everyone on the same timeline instead of turning every gameplay moment into a custom networking message.

The core idea

Beast Smash does not ask the network to decide who hit whom. EasyNet keeps the match aligned, and the deterministic game rules produce the result.

This also makes cheating harder in the places that matter. A client can try to act, but cannot simply claim that an opponent was hit or that a launch happened differently.

Result

The economics made the architecture practical.

Beast Smash reached more than 500,000 downloads on Google Play, more than 70,000 daily active users, crossed 1,000 concurrent players and generated around $5,000 per month from ads alone. The architecture had to keep that scale profitable, not turn it into an infrastructure problem.

Why it matters

The pattern fits more than one fighting game.

Beast Smash made the problem obvious because combat is timing-sensitive, but the same pressure appears in arena games, co-op action, party games and short competitive sessions. When player hosting is too fragile and full server simulation is too expensive, deterministic multiplayer gives mobile games a practical middle path.
